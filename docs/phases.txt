## Decisions Requiring Approval

### Q1: How should category data be extracted from the PDF?

- Extract manually by reading the PDF and building a mapping of school → category.
- Use a PDF text extraction tool to pull the data programmatically, then manually verify.
- Provide a pre-processed list if one is available.

### Q2: Should TVET/STEM/SEN pathways be built now or deferred?

- Build the general selection workflow first (Phases 1–5, 7–8), then add pathways once the core is solid and appendix data is extracted.

### Q3: Should the app persist selections using localStorage?

- Use localStorage. It's simple, requires no backend, and prevents frustration if someone accidentally closes the browser. Document what is saved and where.

### Q4: Should the existing `school-data.js` be enhanced or should a new file be created?

- Create `js/school-data-enhanced.js` that imports the existing data and augments it with categories, codes, and appendix flags. This preserves the original dataset while keeping enhancements separate and maintainable.

- **DECISION (Phase 1, applied):** augment **in place** in `js/school-data.js` (single source of
  truth). `js/school-data-enhanced.js` does not exist and was not created. All pre-existing
  field values are preserved (verified against `data/school-data.baseline.json`); the new
  fields are `code` and `programs_code`, and `classification` is replaced with register-derived
  labels. See `docs/DATA_EXTRACTION.md`.

### Q5: Is the Appendix 3 school list available?

- The PDF should contain it, but a separate, verified list would save extraction time and reduce errors.

## Summary

The critical path is Phase 1 (category extraction). Without school categories, the core validation cannot work. The recommended approach is to proceed with vanilla HTML/CSS/JS, reuse the CSS tokens, and build the phases in order, prioritizing data accuracy over completeness.

Implementation should begin after the approach has been reviewed and approved.
